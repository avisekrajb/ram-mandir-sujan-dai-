Confidential – contains security findings

Security audit report

Shree Ramchandra Temple website (backend API, website, deployment files)

Audit and fixes done on 5 October 2026. Project folder: Desktop\New folder

Please do not email, upload or share this file outside the people who run the site: it explains where the weak points were. It contains no passwords or keys.

1. Summary

The site was reviewed from three directions at once: the server code (every route and controller), the website code (every page, form and link), and the secrets, deployment and dependency files. The weak points were then tested for real against a throw-away copy of the server (never the live data), the fixes were written, and the same attacks were run again to prove each fix works.

The three things that matter most
  1. The secret key that signs every login, and the super-admin password, are weak (a readable phrase and 6 digits) and the same copy is inside backend.zip. Anyone who has seen that zip or the .env file can act as any user. These are yours to change: they cannot be fixed from code. Section 3 gives the exact steps.
  2. The fixes are running on your computer, not on the live website. The local backend on port 5000 had stopped, so it was started again with the new code (check done: protection headers present, super admin untouched, site pages load). It runs as a background task, so after a reboot start it yourself: node --require "..\..\_dev-tools\dnsfix.js" server.js from backend\backend. Your live server needs the new code deployed and the settings in step 6 below, and the website needs a rebuild.
  3. The production settings file is still an unfinished template (placeholder web addresses, live payment mode). If the website is built from it, logins and donations would be sent to an address that is not the temple's. A build now refuses to run until it is fixed.

What was not touched: the live database, the real .env files, the two zip files, and the other Claude sessions' running servers. One note: while checking, an update of the website's software libraries briefly broke the shared development server on port 4000; it recovered by itself after a file nudge and nothing was stopped.

What visitors will notice

  • Passwords must be at least 8 characters and not a common one (the sign-up, reset and change screens say so).
  • The password-reset code has 6 boxes (paste works). "Forgot password" says "if an account exists…" for every address.
  • Subscribing to updates works for the signed-in person's own address only.
  • Signing in with Google or an e-mailed code for an e-mail that was first registered with a password replaces that old password once and sends an e-mail saying so (they can choose a new one with "Forgot password"); this stops someone who registered another person's address in advance. People who already signed in with Google are not affected.
  • The ceremony list on the booking page looks the same in every language; the English name is what is stored.
  • The test-payment logins (eSewa/Khalti sandbox) are hidden on a production build.
  • Photos uploaded by visitors are pictures only (5 MB profile, 10 MB payment screenshot).

5. Recommended next steps (not done)

  1. Two-step sign-in for the super admin and admins (authenticator app or passkey). This is the single biggest protection left.
  2. Verify e-mail addresses at sign-up (a link or code) before an account can send mail or make bookings.
  3. Shorter staff sessions (for example 12 hours) or secure cookies for the admin panel instead of the 30-day token in browser storage.
  4. Move the website build away from Create React App (no longer maintained) to Vite; this clears most of the 70 remaining build-tool warnings.
  5. A monthly routine: npm audit in both folders, update, run the tests in _dev-tools\security-audit\tests.
  6. Put the site behind Cloudflare (free plan) for bot filtering and DDoS protection, and turn on Atlas alerts for failed logins and unusual traffic.
  7. If the API ever runs on more than one server, replace the in-memory rate limiter with a shared one.

6. How this was checked

  • Three independent read-only reviews (server code, website code, secrets and deployment files) produced the findings; each claim I acted on was re-checked in the real files first (for example the secret shapes, the Dockerfile, the footer code, the donation-switch bug).
  • Live attack tests on a throw-away server (own database on a different port, mail, payment and Cloudinary switched off): injection, forged tokens (alg:none, wrong key, expired), cross-account access, role escalation, cross-site calls, oversized and malformed requests, file-disclosure paths, rate limits, and all 256 routes called as visitor and as ordinary user. 112 checks (three suites), all pass.
    • The first run found real gaps (headers, enumeration, weak passwords); the re-runs after the fixes confirm they are closed.
  • Browser tests with headless Chrome: poisoned map, footer and live-video values are neutralised, nothing executes, the 6-box reset code accepts a pasted code, and the booking list shows Nepali names while sending the stored English value. 11 checks, all pass.
  • Content-policy trial across 15 pages: no violations except the development hot-reload socket.
  • An independent review of the fixes themselves was run afterwards: it found 13 problems in the first version of the fixes (section 4, last table); 12 were fixed and re-tested, one accepted. It also checked about 60 other things and found them sound.
  • Upload limits were proven with the real upload code and the upgraded multer library, Cloudinary itself replaced by a stand-in: 5 MB / 10 MB caps, no video, SVG or GIF, one file only (9 checks, all pass).
  • Not tested: real e-mail delivery after the mail-library upgrade; uploads to the real Cloudinary account; real eSewa/Khalti/ConnectIPS payments; the Docker image build; a full production website build with the headers on the real host. Please test those once after deploying.

Tests and tools are kept in _dev-tools\security-audit\ (tests\ for the automatic checks). Pre-change copies of every file touched are in _backups\security-audit-pre\. Both folders can be deleted when you no longer need them, but keep them out of zips and out of git.
